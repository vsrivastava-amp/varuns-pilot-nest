Title: Calibrate the KVSS score coefficients (kvssScoreLinearA/B) for 3.0 unified ranking

Suggested placement: project AI, child of AI-1549 (H2 2026 Ranking and Pricing Engine, Yield-Based Ranking). Link AS-13428, AI-1436, AI-1435.

Placement note: AI-1513 was the earlier candidate. AI-1549 is the better home because AI-1513 closes once AAS supports text ads, and this question outlives that. Ranking calibration is what AI-1549 already covers.

Description:

Discover 3.0 ranks product ads and text ads in one list. In AAS, DiscoverRankingStep sorts on normalizedScore alone, regardless of ad type (DiscoverRankingStep.java:63, :199, :216).

The two ad types reach that score by different formulas.

* Text ad: normalizedScore = floor((a * rawKvssScore + b) * 1000000), where a and b default to 0.93 and 0 (KvssProperties.java:43-44, KvssScoreNormalizer.java:48-49). KVSS returns a raw score in [0,1].
* Product ad: normalizedScore = floor(score * 1000000) (ProductAdResultMapper.java:78).

So inside AAS, a and b set the text-vs-product mix of every 3.0 auction.

Why now:

AS-13428 moved to Ready for QA on 2026-07-28 and was handed to QE on build dsp-engine 1.1.1127-release-discover-3_0-text-ads. Its acceptance criteria require test coverage of mixed text and product results. Someone is about to evaluate an ordering that these coefficients set, so the value should be a decision rather than a leftover.

Where 0.93 came from:

The history in ad-auction-service records the changes but no reasoning.

* 2026-07-10, commit 597bb0f, "AI-1435 - integrate text ads into discover auction". Java default and application.yml both set a = 1. The transform starts as identity.
* 2026-07-14, commit 056e61d, "AI-1435 - cleanup". application.yml moves to 0.93. The Java default moves to 0.8. The same commit adds the javadoc paragraph explaining a = 0.8, on the grounds that VSS full-title cosine similarity is a stronger relevance signal than a KVSS short-phrase match.
* 2026-07-15, commit 73a414f, "AI-1435 - address CR". The Java default moves from 0.8 to 0.93. The javadoc still explains 0.8 and still does at HEAD (KvssProperties.java:38).

Two consequences follow.

1. application.yml sets the property in every environment, so 0.93 is the value that has always run. The Java default of 0.8 never took effect anywhere.
2. The javadoc now documents a value that nothing uses. That is a small fix and worth doing regardless of the calibration outcome.

The direction of the adjustment is defensible. Discounting a text ad below a product ad at equal raw score matches the javadoc's argument about the two relevance signals. The magnitude is the open question. Nothing in the repo distinguishes 0.93 from 0.8 or from any other value.

Open question to resolve first:

AS-13428's technical notes give the DSP-side yield formula as rankingScore * ctr * advertiserBid, descending, with creativeYield as the tiebreak. That ticket also says the dsp-engine comparator selects the relevance signal by ad type, and for TEXT it names "Elasticsearch or keyword relevance score" rather than the AAS normalizedScore. So it is unclear whether AAS's 0.93-scaled score is the rankingScore that DSP multiplies, or whether DSP derives its own text relevance signal. I have not read dsp-engine PR 841. This changes the scope of the work, so it should be answered before any calibration effort starts.

* If DSP consumes the AAS normalizedScore, these coefficients reach pricing and yield, not just ordering.
* If DSP uses its own text signal, the AAS coefficients affect only what AAS returns, and there may be a second uncalibrated constant on the DSP side.

Acceptance criteria:

1. Confirm whether the DSP unified comparator consumes the AAS normalizedScore for text ads. Record the answer.
2. Agree a calibration method and run it. Two candidate approaches: align the raw score distributions of KVSS and VSS on matched traffic, or fit against a relevance ground truth. ARES-by-ad-type currently scores product ads well above text ads, which makes it a candidate anchor. That observation comes from Tarun's 7/13 analysis and needs re-checking before it anchors anything.
3. Set a and b from that analysis. State explicitly whether b stays at 0.
4. Make the javadoc, application.yml, and the recorded rationale agree on one value.
5. Record the decision before 3.0 text ads ramp past experiment traffic.

Both coefficients are already overridable per request through the experiment keys kvssScoreLinearA and kvssScoreLinearB (ExperimentContextReader.java:23-24), and per environment through KVSS_SCORE_LINEAR_A and KVSS_SCORE_LINEAR_B (application.yml:105-106). Calibration needs no new instrumentation.
