## Service internals worth knowing (learned 2026-07-22, AI-1474 scoping)

- **The civ "cache" is DynamoDB in the service** (`persistence/dynamodb_repo.py`, table `civ_label` via `CIV_TABLE_NAME`). Cache key = `sha256("<evalId>|<lower(trim(qt))>")` — **namespaced by eval_id**, so a new eval_id starts with a clean cache; old misclassifications can't leak in. Busting options: `bypassCache: true` per request (still writes results back), `DISABLE_CACHE=true` env (kills reads+writes), `POST /v1/intent/civ/invalidate-cache` (delete by evalId+qt). Cache hits are re-validated against current pydantic/taxonomies; schema-valid-but-wrong entries survive.
- **Model registry** = `llm/config/models.json` (the allow-list of `model_id`s; provider=databricks AI gateway, OAuth). Endpoint resolved per-domain via `domain_endpoint_name` — civ passes `domain="civ"`; models without a `"civ"` key fall back to `default` (e.g. `gpt-5-2` → `ai-gpt-5-2`). New eval config = one entry in `domains/<domain>/eval_configs.json` (+prompt file if new) + model present in models.json + **redeploy** (configs are `@lru_cache`d at process start). `evalId` is an unvalidated int in the request schema; unknown ids fail deep in llm.py as KeyError.
- **Prompt caching is real and huge**: the civ system prompt (~16.4k tok — embeds full GPC tree with IDs + IAB taxonomy) is resent per LLM call; OpenAI-side auto prefix caching (≥1024 tok) gives **93–97% of input tokens as cache reads** (verified in `system.ai_gateway.usage.token_details.cache_read_input_tokens`). The `cache_control: ephemeral` block in `invoker_unstructured.py` is Anthropic-style and a no-op for OpenAI models. Cost estimates that ignore this run ~10× high.
- **Observed civ latency** ≈ 5s/LLM-call (gateway telemetry, nano and mini alike).
- Civ LLM returns integer GPC leaf IDs; `llm.py` resolves them to path strings via `resources/gpc_taxonomy.json`; `validation.py` drops paths not in `taxonomy.en-US.txt`.
- **Civ API failure modes under batch load (mapped 2026-07-27/28, AI-1474 cache refresh — per-item diagnostic in `dev_amplify.elme_l3_keyword_categorization.civ_refresh_diag_ai1474`):**
  - Batch responses are 200/207 with **per-item status** — always inspect `queries[].status`/`error`, never infer success from HTTP status or GPC presence.
  - **FAILURE 422 "LLM returned invalid taxonomy values"** ≈ 6% of items on nano+v3: LLM call succeeds (gateway shows 200 — invisible in `system.ai_gateway.usage`) but hallucinated GPC/IAB strings fail validation → item NOT cached. Largely transient: retries resolved 126/129, most gaining valid GPCs. The invalid-**iab** variant discards a *valid* GPC along with the bad IAB.
  - **SUCCESS with empty GPC** ≈ 19% on nano+v3 for advertiser keywords that all had GPCs under mini — legit answer, IS cached. v3 is much choosier than mini; expect no-GPC rates in the 20% range on keyword-targeting sets.
  - **Whole-request 503s** ~1-2 per 90 long batch POSTs (200 queries ≈ 30-60s connections) — LB/pod cycling; entire batch unprocessed; idempotent re-run covers it.
  - **Per-item 429 RESOURCE_EXHAUSTED** appears inside 207s under concentrated bursts (tight retry loops on few queries).
  - **The API path persists to DynamoDB ONLY.** `prod_amplify.llm_evals.ad_request_civ` is the *offline batch pipeline's* sink (real ad-request ids; ~95M rows/day) — API calls leave no Databricks trace, so diagnostics must capture response items themselves. NB: that table's no-GPC rows conflate legit-empty with 422 failures.
- **Local dev auth (undocumented in the README — trips new setups):** running the service locally against the dev AI Gateway needs `DATABRICKS_CLIENT_ID` / `DATABRICKS_CLIENT_SECRET` — a **service principal, not a personal PAT** (`providers.py` hard-requires it). The team's **shared dev SP** lives in **Keeper: record "ml-llm-dev DBx OAuth [DEV]"** (Varun shares it per-person); drop the two values into your local `.env`. It's already scoped to the dev gateway, so no need to mint a new one. If a fresh SP is ever needed, gateway SPs/endpoints are provisioned by **infra (Pun Tong)**. (Surfaced 2026-07-23 when Yaarit hit this on a new laptop.)

- **pciv_online domain (branch `feat-online-pciv`, 2026-07-24, unmerged — worktree `~/Documents/llm-evaluator-service-online-pciv`)**: copy of civ_extraction at `/v1/intent/pciv` for the online Qwant path. Facts that outlive the branch:
  - **Eval-ID namespace is global across domains**: the DynamoDB `civ_label` cache key has no domain component, so a second domain reusing IDs 2-8 would poison/share the civ cache. pciv_online reserves **≥101** (101 = nano+offline civ prompt, 102 = nano+conversation pciv prompt from pciv-demo-service `dev-taxonomy-full-l2`, 103 = bedrock ministral-3-8b).
  - **`bedrock` model_provider** now exists in `llm/utils/providers.py` (`ChatBedrockConverse`, default boto3 credential chain — AWS_PROFILE locally, IRSA in k8s; `bedrock_model_id` key in models.json). Gotcha: the invokers' `cache_control` content block is OpenAI/Anthropic-style and **Bedrock Converse rejects unknown content keys** — it's now sent only when the model class is ChatOpenAI.
  - **Mantle IAM has two independent gates** (verified in dev 2026-07-30): `bedrock-mantle:CallWithBearerToken` authorizes bearer-token use, while `bedrock-mantle:CreateInference` authorizes the inference request. The first alone returns HTTP 401 naming the missing `CreateInference` action. AWS's `AmazonBedrockMantleInferenceAccess` managed policy includes both (plus Get/List project access); a custom workload policy must preserve both.
  - **Smoke test**: `AWS_PROFILE=dev PYTHONPATH=src/main/python .venv/bin/python scripts/pciv_online_smoke.py --eval-id 103` — one tiny call; self-resolves bedrock model id + `us.` prefix against the live catalog and prints any models.json correction.
  - **requirements.txt is uv-compiled from pyproject** (Dockerfile installs from it). Regenerate with `uv pip compile pyproject.toml -o requirements.txt --python-version 3.13` — **without `--python-version 3.13` uv resolves for an older Python and silently downgrades pins** (numpy 2.4→1.26, databricks-connect 17→16).

## Model gateway / registry (how models get onto the eval service)

- The eval service runs on the **Databricks model gateway** (AI Gateway / Foundation Model APIs). Two layers:
  1. **Foundation model catalog**: `databricks-<model>` pay-per-token endpoints (FOUNDATION_MODEL_API). Browse: UI `/ml/ai-gateway` per workspace, or CLI `databricks api get /api/2.0/serving-endpoints -p <profile>` (filter `FOUNDATION_MODEL_API`; `creation_timestamp` reveals recency). Dev had 49 endpoints on 2026-07-23; newest: gemini-3-6-flash + gemini-3-5-flash-lite (added 2026-07-21), inkling (07-15), gpt-5-6-luna/terra/sol (07-09), claude-sonnet-5 (06-30), glm-5-2 (06-23), claude-fable-5 (06-09). Databricks tracks frontier releases within days-weeks.
  2. **Named wrapper endpoints** the service actually calls (`ai-gpt-5-2`, `civ-gpt-5-mini`, `ares-gpt-5-mini`…), mapped per-domain in the service's `llm/config/models.json`. Created by **infra (Pun)** — but infra cannot set rate limits.
- **Rate limits are per WORKSPACE per MODEL, in tokens** (ITPM = input tokens/min, OTPM = output tokens/min) — not per-endpoint, not per-request. Set by **Databricks** (contact: Sixuan He, external Slack channel; they can query current limits per workspace/model). Snapshot 2026-07 (prod 5702410742425796): gpt-5-mini 150M/20M, gpt-5-4-nano 90M/6M; dev: mini 40M/4M, nano 20M/2M; un-negotiated models default tiny (haiku-4.5 = 1M/0.1M everywhere; gpt-5-2 effectively unusable → the 429 storms). **Sizing**: rpm × tokens-per-request must fit ITPM; evidence suggests ITPM counts cache-read tokens (nano's observed ~100M tok/min peak ≈ its 90M ITPM) — confirm with Databricks. Capacity ask flow: (1) Pun creates endpoints, (2) Databricks sets model ITPM/OTPM (ask template: git history of REVIEW.md, 2026-07-23 v3 entry — REVIEW.md deprecated 2026-07-27).
- **Pricing**: Databricks charges *pretty close* to the official provider list prices (OpenAI/Anthropic/Google). DBX's own pages lag: https://www.databricks.com/product/pricing/model-serving and https://www.databricks.com/product/pricing/foundation-model-serving. For OpenAI-family models, check openai.com model pricing directly and assume ≈parity. Empirical per-run cost: measure via `system.ai_gateway.usage` token counts (see telemetry below) × provider list price.

## Pipeline mechanics

- **Ares (relevance)**: scheduled batch. Lower bound = `pipeline_metadata.data_pipeline_offset` row (`pipeline_name='ad_relevance_evaluation'`) taken **verbatim** — nothing floors it. No row ⇒ defaults to `now()-20min`. Run unions retry-eligible rows from `ad_relevance_failures`, and the committed offset = max over that union (can move the offset *backward*). Row requires non-null `batch_id` (use `'0'` when seeding).
- **Civ**: continuous streaming, `startingVersion: latest`, checkpoint at `/llm_evaluation_pipeline/ad_civ_extraction_pipeline/checkpoint/<env>/ad_civ_extraction`. Stale checkpoint ⇒ huge catch-up; delete `offsets/commits/metadata` to reset (dev has a teammate's `sjain-local` dir alongside — preserve). **Civ backfill** job takes `--start_date/--end_date`, anti-joins `ad_request_civ` (only unevaluated rows), and is the reliable way to test civ e2e.
- Writers `MERGE INTO` — output tables must pre-exist (`ad_request_civ`, `ad_request_civ_failures` were created in stage from dev DDL during this release).
- A few % retriable failures per run is normal (handled by failure-retries job).

- **First latency taste** (laptop → us-east-1, 3-token converse, single sample — NOT a benchmark): ministral-3-8b 370ms, qwen3-32b 373ms, haiku-4-5 904ms (us. profile), llama4-maverick OK. In-network from RIC1 should match or beat this.
- **Mantle locality + latency topology (verified 2026-07-31):** the pCIV finalist configs explicitly use `region: us-east-1`, which constructs `bedrock-mantle.us-east-1.api.aws`. AWS's current model cards label Luna, Gemma 4 31B, Qwen3 Next 80B, and Ministral 14B as **In-Region in us-east-1** and give all four no Geo or Global inference ID; AWS defines In-Region as keeping the request within one Region. In the deployed test path, Databricks does **not** call Mantle: DBX → `online-pciv-service` → Mantle, and the service pod is on dev EKS us-east-1. Therefore `summary.processingMs` is the existing EKS-side same-region service timing, while harness `e2e_ms` additionally includes DBX→ingress/network time. For the 2026-07-30 single calls, that outer delta was Gemma 59ms, Luna 17ms, Qwen 17ms, Ministral 21ms. Do not call those a benchmark: n=1, 18–23k offline prompt, no cache reads, and unknown warm/cold state.
- **Production-shaped E2E benchmark:** run the load client from the actual SSP pod or a temporary pod/EC2 in the same us-east-1 VPC/cluster and call the same service address SSP will use (prefer Kubernetes service DNS over the dev ingress if that is the intended production hop). Use the exact ~3.6k pCIV prompt/request shape, persistent HTTP connections, app-cache bypass, interleaved models, 5–10 warmups, and n≥50/model; report p50/p95/p99 for both caller wall time and server `processingMs`. A direct EC2→Mantle call is useful only to isolate provider latency; it is not service E2E. Add a provider-call timer/span around `model.ainvoke` if provider-only percentiles are needed.
- **Mantle PrivateLink status (verified live 2026-07-31):** AWS exposes `com.amazonaws.us-east-1.bedrock-mantle` as an Interface endpoint service in `us-east-1a/1b/1d`, private DNS name `bedrock-mantle.us-east-1.api.aws`, with no acceptance requirement. Dev EKS `eks-dev-use1-01` is in VPC `vpc-0317d6910f3add39a`; neither that VPC nor any VPC in dev account 564079877134 has a `bedrock-mantle` endpoint. A DNS-only SSM probe from an actual dev EKS worker resolved the Mantle hostname to public addresses `3.214.115.45`, `52.87.73.163`, and `34.231.48.123`, definitively excluding a centralized DNS override/PrivateLink path. Therefore dev pCIV currently reaches Mantle's regional public endpoint. To close the gap, infra creates an Interface VPC endpoint in the workload subnets/AZs, enables Private DNS, permits HTTPS from the pod/node path, and applies an endpoint policy allowing the required Mantle actions. With Private DNS enabled, the existing application hostname and code stay unchanged. Repeat per stage/prod VPC; endpoints are VPC-scoped.
- Gotchas: laptop CLI is `aws-cli/2.16.3` (June 2024) — **lacks `bedrock list-inference-profiles`**; use the `us.<modelId>` convention for INFERENCE_PROFILE models, or upgrade the CLI. `INFERENCE_TYPE` per model in `list-foundation-models` output tells you which need the prefix.
